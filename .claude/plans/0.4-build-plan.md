# ntm 0.4 build plan

Written 2026-11-08 for the owner and for the worker agents, from
`.claude/DECISIONS.md` (0.4: decided, 0.4: setup, Deferred and open) and the
2026-11-07 review. Revised the same day after three critics read it, after the
owner answered its open decisions, and again after the owner reshaped 0.4 that
night (section 9, Decided). What the reshape left for the owner is in section 6,
"For the owner".

Words: "the base" is the published plugin, `ntm`. "The user plugin" is the
generated one, `ntm-user`. "The Settings document" is the document on the user's
todo list that holds their values; "the Style document" holds their persona's
Profile. "The build" is setup's step that writes `ntm-user`.

## Owner answers after review (2026-11-08); they override the text below

  are built into `ntm-user:backend`.
- No alias plugin, and no README line about one.
- Chat and Cowork are one host now; don't split steps by host.

  base `reminder --type`, morning's own skill calling it, customization in the

- Each PR carries its own concept with its change; this file is a working plan,
  not something the owner reviews.

## The shape in one page

- No rename. The base stays `ntm`, the user plugin stays `ntm-user`. Day to day
  commands are base skills called directly: `/ntm:today`, `/ntm:plan`,
  `/ntm:pause`. There are no entry skills. Users rarely type commands; their
  jobs do most of the calling, and a job's prompt loads `ntm:<skill>`.
- The base keeps every procedure that is the same for everyone: `plan`, `today`,
  `show-completed`, `fix-todo-list`, `pause`, `review-todo-list`, the three
  reminders, `price-watch`, `sync-price-watch-to-amazon`, `help`, `self-test`,
  `settings`, `ready-check` and the three agents. It gains `setup`, a tiny
  `update`, `schedules` and `style`. It loses `conventions`, `notify` and every
  `configure` skill.
- A base skill says WHAT to do and asks `ntm-user:backend` for the data, in
  plain words: `ntm:today` is "get today's open items from `ntm-user:backend`,
  then present them". Planning, the reminders and the price watch all work this
  way, and future recurring items will show up in "today's open items" the same
  way.
- `ntm-user:backend` is the one place that teaches how to work with this user's
  list: their backend's calls, their labels and statuses, what counts as open,
  where every document lives (Settings, Style, each database). It is the list
  rules and the backend guide, tailored to this user and nothing else.
- The generic text (the list rules, every backend guide, each feature's rules)
  lives in the base only as setup reference files the build reads. A rule fix
  reaches users through `update` and a rebuild, not a base patch. Tokens matter
  most, so the owner accepts that.
- The hard rule: no day to day run loads text about a path the user isn't set up
  for (another backend, a feature they didn't pick). Text a base skill needs for
  one feature lives in a reference that only that feature's runs load.
- The user plugin holds two skills: `backend`, and `notify` (their channel, plus
  the Pushover keys when they use Pushover); plus the Linear connector for
  Linear users. `ntm:settings` and `ntm:ready-check` are base skills that ask
  `ntm-user:backend`: `settings` for the Settings document, `ready-check` for
  the ping.
- Values setup collects live in the Settings document, except the Pushover keys,
  which are built into `ntm-user:notify`. The persona's Profile lives in the
  Style document, which the base's `style` reads.
- Setup is one wizard with a reference file per step. It saves at the end of
  each area. It ends with one handoff prompt: run `/ntm:self-test`, then
  `/ntm:schedules --setup "<schedules and model>"`. A passing self-test sends
  the success message. The Settings document holds no schedules; the scheduled
  tasks are the source of truth.

## 1. The base plugin: every file

### Rules that apply to every base file

- Calls name the plugin: `ntm:<skill>` for a base skill, `ntm-user:<skill>` for
  a user plugin skill. Base-to-base calls already read `ntm:<skill>` on main and
  stay as they are.
- A base skill asks `ntm-user:backend` for what it needs in plain words
  ("today's open items", "everything done last week", "set the planned date of
  ABC-12 to Friday"). It never names a backend's tool, a status's name or a
  database's location. Label names keep the `$` notation (`$price-watch`);
  `ntm-user:backend` says what each one is called.
- Feature text loads only on that feature's runs: `self-test`'s price watch
  steps go to `self-test/references/price-watch.md`, read only when the Built
  line names price watch.
- Base skills keep their full descriptions; with no entry skills, they are what
  triggers.
- A skill that hands work to an agent keeps one line for when the agent isn't
  loaded (chat ignores agents): read `agents/<name>.md` from the newest
  installed `ntm` and follow it. This replaces conventions' "Chat, jobs and
  agents" section.

### Kept

Each keeps its name and its procedure. The edits are the 0.4 wiring.

  and every operation name become requests to `ntm-user:backend`.
- `pause`: the same, and its database is titled `Paused dates`, with a line at
  its top saying what it holds.
- `review-todo-list`: the same; when Estimate pattern is blank, it asks the one

- `price-watch`, `sync-price-watch-to-amazon`: the same; their job run block

- `help`: finds the newest installed copy when several sit side by side (synced
  uploads keep generations: `ntm` 0.3.0 beside `ntm~g2` 0.3.2); answers "which
  version is installed" from the base's plugin.json and the Built line.
- `self-test`: the loop through `ntm-user:backend`, the base-only path, the

- `agents/messenger.md`: loads `ntm:style` and `ntm-user:notify`, and asks
  `ntm-user:backend` how to word a task where it read conventions' "Talking to
  the user about tasks".
- `agents/estimator.md`, `agents/shopper.md`: ask `ntm-user:backend` where they
  loaded conventions.

## 2. The user plugin

### Layout

```
ntm-user/
    .claude-plugin/plugin.json
    .mcp.json                     Linear users only: the connector
    skills/backend/SKILL.md
    skills/notify/SKILL.md
```

No references folder, no agents, no README.

### What each skill holds

- `backend`: the Built line; the core rules; the rules for each feature the user
  picked, and only those; their labels, statuses and Deviations written in;
  their backend's calls (on Linear, the guide's operations with this team's name
  and id; on their own backend, their description per contract heading); where
  every document lives: Settings, Style, and each database their features use.
- `notify`: the one channel they picked, from `notify/pushover.md` or
  `notify/claude-push.md`, as written; on Pushover, with their user key and
  default app token filled in.

Gone from the user plugin: `ntm-user:style` (the Profile is the Style document;
`ntm:style` is the procedure), `ntm-user:settings` (the values are the Settings
document; `ntm:settings` shows them), a user `self-test` (the base's runs as
`/ntm:self-test`), and every entry skill.

By backend: on Linear, `.mcp.json` is `backends/linear-mcp.json` copied as
written; the synced 0.3.0 upload shows the shape, `mcpServers.Linear` as
`{type: http, url: https://mcp.linear.app/mcp}`. On their own backend, no
`.mcp.json`.

### How the build writes it: a guide, not templates

`setup/references/build.md` says, per file, what it must hold and where each
piece comes from. Two kinds of text, and the guide names which is which:

1. Written from the guide with the user's values: the Built line, plugin.json,
   `backend`'s list of documents and where each lives, and `backend`'s calls on
   their own backend (from `backends/contract.md` and what setup wrote with
   them).
2. Copied as written from a base reference, with the user's values filled in:
   the rules files for their features, the Linear operations, `.mcp.json`,
   `notify`'s channel and its Pushover keys. The guide says "as written, never
   retyped".

Last check before zipping: no `<` or `>` in any SKILL.md description or in
plugin.json's description (the uploader rejects them).

Then: zip, present it (the outputs folder in chat, a path under the working
directory for Chrome), install through the accept card or Customize > Plugins,
and hand off (section 4, step 9).

### plugin.json

```
name          ntm-user
displayName   ntm-user
version       0.4.<rebuilds>                  0.4.0 on first build
description   one sentence: your ntm, your todo list on Linear,
              reminders by Pushover; no date, no angle brackets
generated     2026-11-08T14:30Z               (unknown 4; if rejected,
                                               the description carries
                                               it)
```

### The Built line

`ntm-user:backend` opens with one line:
`Built: ntm-user 0.4.0 from ntm 0.4, 2026-11-08 14:30 UTC. Backend: Linear. Channel: Pushover. Features: task management, price watch.`
Every run loads `backend` anyway, so the line costs nothing to read. `update`
reads `major.minor`, the choices and the features from it; `self-test` reads the
features. The build writes it and plugin.json in one step.

### The Settings document's place in the build

The Settings document is the one home of the values setup collects, except the
Pushover keys (section 3). Some are read live; some are built into
`ntm-user:backend`:

- Read live: About you, Planning, Shopping, Notifications. A change takes effect
  on the next run.
- Built in: Labels and Deviations. A change is made in the Settings document,
  then `update` rebuilds. `ntm:settings` says which is which.

## 3. The Settings document

Title `Settings`, a document on the todo list like the other databases; on a
backend without documents, a task's description. Setup creates it when it saves
the todo list area, after the ping, with the backend reference it is following;
each later area adds its values when saved. Free text under fixed headings, read
by heading; a missing section means its defaults.

```
## About you          Timezone; Country and currency (price watch only)
## Labels             the label lines; built in
## Planning           Estimate pattern (blank until the first review);
                      Excluded labels from automatic scheduling
## Shopping           Amazon interface; anything about how they shop
## Notifications      how they want to be notified, as written
## Deviations         anything they do differently; built in
```

No Schedules heading: the schedules and the jobs' model go in setup's handoff
prompt.

Who reads each, always by asking `ntm-user:backend` for the section: About you,
the shopper and `schedules`; Planning, `plan`, `review-todo-list` and the
estimator; Shopping, the shopper, `price-watch` and
`sync-price-watch-to-amazon`; Notifications, `ntm-user:notify`. The build reads
Labels and Deviations. `ntm:settings` shows the whole document.

Backend, List name and List id aren't in it: they're built into
`ntm-user:backend`, since reading the document needs them. The channel and the
Pushover keys (user key and default app token) are built into `ntm-user:notify`;
a job's own app token goes in its prompt.

### Databases and where they live

Every database has one owner skill that creates it the first time it writes;
setup creates only Settings and Style, and confirms the names of the rest (step
8). `ntm-user:backend` says where every document lives: Settings, Style and the
databases the user's features use.

- `Settings`: setup; shown by `ntm:settings`.
- `Style`: setup (the Profile); revised by `ntm:style` on request.
- `Paused dates`: `pause`, with a line at the top saying these are the days
  nothing gets planned automatically.
- `Message history`: `style`, with the default frontmatter
  `Keep: 60 entries or 8 weeks` when missing.
- `Task review log`: `review-todo-list`.
- `Price watch stores`: `price-watch`, in the project with $price-watch.

#### Step requirements from 0.4: setup, for the workers

Each is an acceptance check for the PR that writes that step's file.

- Step 1 (PR 44): the intro from the draft; ntm says "I", the owner is "my
  creator"; ends by confirming the timezone.
- Step 2 (PR 37, PR 39): suggest a free Linear account, help create and connect
  it, and ping right then. Someone who doesn't want Linear hears it takes
  longer, and that you're happy to: read the contract and search with them until
  they're content, always offering to build the list inside Claude (an artifact
  or a Claude Doc; only what unknown 8 proved) or to find an existing tool.
  Saving the area creates the Settings document with the timezone.
- Step 3 (PR 38): right after the list. Push a little when they decline: without
  a persona, ntm is no different from Apple or Google reminders. Build from
  generic parts, no show or IP named, repetition guarded. The opener: "think
  about the formula of a show you enjoy, where they can snap back at you when
  you need it, or celebrate you when you've earned it". Saving the area writes
  the Style document, in the persona contract's sections.
- Step 4 (PR 40): a numbered list, everything or a subset: day to day task
  management, and price watch.
- Step 5 (PR 40): task management: suggest Monday to Friday for doing things and
  Sunday for cleanup and planning the week ahead, the Sunday job as the
  suggested weekly composition; then its labels, $pending-shipment included even
  without price watch. Price watch: country and currency; the schedule, the
  owner's (daily) as the default; its labels; then Amazon sync, explaining that
  cloud agents can't reach Amazon, so this works around it; a no skips the
  Amazon labels too. Show the table (job, days, time, title). Saving each
  feature's area saves its labels and values to the Settings document; its
  schedules are held for the handoff prompt.
- Step 6 (PR 49): one question, "a lighter model than the one running this
  chat", worded for any AI provider, no model names. It goes in the handoff
  prompt with the schedules.
- Step 7 (PR 41): for a separate app on their phone or computer, strongly
  suggest Pushover, which their phone's focus settings can treat differently;
  otherwise the AI app's own push. The keys, one test push with explicit keys,
  then how they want to be notified. A job's own Pushover app isn't asked; it
  stays in `notify/pushover.md`.
- Step 8 (PR 43): confirm the names of the databases their features need; on
  Linear, that they live at Linear's base location and which document holds
  which. Creates none.
- Step 9 (PR 48, PR 49): say what's about to happen and wait for a green light,
  leaving room for anything else they want to say. Then one narrated line per
  step: write the plugin, install it, hand off. The handoff prompt, the same
  text for a subagent or a new chat: "I just set up ntm and need you to run
  tests and finish the setup. Run `/ntm:self-test`. If it passes, set up the
  schedules: `/ntm:schedules --setup "<schedules and model>"`". A subagent
  first, since a new plugin may only load in a fresh session (chat has none, so
  chat always gives the prompt to paste). If that fails, the user pastes it into
  a new chat, or setup drives their browser, only when it has browser access.
- Step 10 (PR 27): a passing self-test sends the success message in the persona,
  said in chat and sent as a push. Then `schedules --setup` creates the jobs.
  The setup chat never learns that self-test passed on the new-chat path, so it
  can't send the message itself.

### update

Tiny. Its whole body: load `ntm-user:backend`; if it won't load, ask "It doesn't
look like you've run setup before, do you want to?" and on yes load `ntm:setup`;
otherwise load `ntm:setup`, which sees the Built line and follows
`setup/references/update.md`. One rebuild path: setup's build.

`setup/references/update.md`: read `major.minor`, the choices and the features
from the Built line; list `update/references/` (the newest file is the base's
version); for each version after theirs, read that file and offer what's new,
features included. Same `major.minor`: "You're current on 0.4", and offer to
change a built-in value or choice (backend, channel, Pushover keys, features,
labels, Deviations). A new feature walks its area as step 5 does. Any change:
the same green light as step 9, then `build.md` with the existing choices
carried over, then the handoff (with `schedules --setup` only for a new
feature's jobs). Nothing is built or installed before the green light; self-test
is never run unasked.

`update/references/0.4.md`: what 0.4 is, and that 0.3 installs start fresh (no
migration), in this order: turn off or delete the 0.3 jobs; install the 0.4
base, which overwrites the 0.3 `ntm` in place (My Uploads matches plugins by
name); run setup, whose build overwrites the 0.3 `ntm-user` the same way. Done
in another order, the 0.3 jobs fail until setup finishes, and the handoff's
`schedules --setup` creates a second set of jobs beside them.

## 5. Contracts between base and user plugin

A contract is a skill the base calls by a fixed name whose text varies per user.
Two, both in the user plugin. Only the names and the shapes below are fixed; the
body is the user's.

### `ntm-user:backend`

A skill, not a service: it is text the running agent loads. A base skill loads
it once, at its first need, and writes each need as one request from the table
("ask `ntm-user:backend` for today's open items"). Under each request, `backend`
gives the call to make (the connector tool and its arguments, with this user's
statuses, labels and ids filled in) and the shape of what comes back, as
`backends/contract.md` gives it for the operations the request uses. The agent
makes the call itself. The requests the base makes:

```
today's open items          open, planned today or earlier
open items planned <span>   open, planned in the span
open items to plan          open, unplanned or stale, not blocked,
                            no excluded label
every open item             with the list's projects
items done <span>           closed in the span
watched items               price watch users only
task <id>                   with its comments
create a task               title, description, labels, parent
change a task               planned date, status, labels, estimate,
                            comment, duplicate of, title, description
read or write <database>    the Settings document or a section,
                            or a database from section 3; self-test's
                            throwaway database is created on its
                            first write
how to word a task          for anything the user reads
ping                        the list answers; on Linear, a bundled
                            server showing only authenticate tools is
                            "Linear needs sign-in", with how
```

A request it can't place gets `Backend CAN'T: <why>`. Each request names the
contract operations it uses, so a user's own backend description, written per
operation, covers every request. New features add requests here and operations
to `backends/contract.md`.

### `ntm-user:notify`

Called as today: `--title`, `--message`, and the optional `--url`, `--priority`,
`--from`, `--app-token`, `--user-key`. Returns `Sent: <title>`, the
`NOTIFY VIA FINAL REPLY` delivery block,
`Notify TOO LONG: <cap and why>; this was <n>`, or `Notify FAILED: <why>`. Caps
stay in the channel's text. On Pushover, its user key and default app token are
built in; `--app-token` and `--user-key` override them.

### The base skills those contracts serve

#### `ntm:ready-check [--notify-failure <skill>]`

A base skill, the same for everyone. Returns `Ready-check OK`,
`Ready-check OK (no style)` or `Ready-check FAILED: <failure> — <fix>`. Its
failure list names no backend. Its one tailored step asks `ntm-user:backend` to
ping; a ping that answers `Backend CAN'T: <why>` becomes
`Ready-check FAILED: <why>`, so a Linear user's sign-in failure comes from
`ntm-user:backend`, not from here. Its failure push goes through
`ntm-user:notify`.

#### `ntm:settings`

A base skill. Asks `ntm-user:backend` for the Settings document, then shows it
or points to the right place for a change (section 1). Returns nothing a skill
depends on.

#### `ntm:style [--stay-fresh] [--for <reminder>] ["<tone>"] <message>`

A base skill. Returns the message, plain text, ending in a `Title:` line under
`--for`. Reads the Profile from the Style document and keeps Message history,
both through `ntm-user:backend`; revises the Profile with the user on request.
Optional: when it won't load, callers use plain words. The persona contract,
`style/references/persona-contract.md`, fixes the Style document's sections,
from `.claude/drafts/persona-breakdown.md` (its components, anti-repetition,
seed prompt; nothing owner-specific).

#### `ntm:self-test`

Returns `Self-test OK` or `Self-test FAILED at <step>: <why>`. With no
`ntm-user:backend` it returns
`Self-test OK (base only): nothing is set up; run /ntm:setup` (publishing needs
the base to pass alone). With one: `ntm:ready-check` (on Linear, the bundled
server's sign-in if it asks), the loop through `ntm-user:backend`, the price
watch steps from `references/price-watch.md` only when the Built line names
price watch. A pass ends with the success message, written by `ntm:style`, sent
through `ntm-user:notify` and said in the reply. It creates no jobs.

#### `ntm:schedules`

The base's scheduling skill, called directly. It checks which scheduled tasks
exist and belong to ntm; with none, it walks the user through setting them up;
with `--setup "<schedules and model>"`, it creates the jobs from that text. The
shapes: the single-skill prompt and the composed prompt below, the cron
expression with `CRON_TZ`, `notifications: {push: true}`, the model set with
`update_trigger`, the jitter rule as "never on :00 or :30". Once created, a job
is the user's scheduled task, and a change to it (time, steps, off, on, delete)
edits that task directly.

A job that runs one skill:

```
<title>.
Timezone: <Timezone from About you>.
[Planning: <what differs from plan's defaults>.]
[Pushover app token for this job: <token>. Hand it to every
ntm-user:notify call as --app-token, and to the messenger as app token:.]
<the job run block, from schedules/references/job-run.md>
Load `ntm:<skill>` and follow it from step 1.
If `ntm:<skill>` can't be loaded, end the run with this line:
`<title> FAILED: ntm:<skill> couldn't be loaded; check ntm is enabled.`
```

The job run block (ready-check first, the final reply, error handling) is
written into each prompt from `schedules/references/job-run.md`, so the
reminders and the price watch drop their copies and no chat run loads it. A fix
to it reaches existing jobs when `schedules` rewrites them, which `update`
offers.

A composed job lists its steps: the same header and block; one
`Load ntm:<skill>` step each, with its span and what to do on its `FAILED` line;
the messenger with every step's lines for one message; the same can't-be-loaded
line. The suggested weekly job: `ntm:show-completed` for the span just past,
`ntm:fix-todo-list`, `ntm:plan --auto` for the next span, then the one message.

## 9. Decided

The owner's answers, 2026-11-08, one line each; the reshape that night overrides
the earlier answers where they differ.

1. No rename: the base is `ntm`, the user plugin `ntm-user`. Base skills are
   called directly; no entry skills; job prompts load `ntm:<skill>`.
2. `ntm-user:backend` is the one place that teaches how to work with this user's
   list; base skills say what to do and ask it for the data.
3. No base conventions skill: the generic text is setup reference, and a rule
   fix reaches users through `update` and a rebuild.
4. No day to day run loads text about a path the user isn't set up for.
5. `setup` and a tiny `update` are the base's entry points; `schedules` is a
   base skill.
6. Setup ends with one handoff prompt (subagent first, else pasted in a new
   chat): `/ntm:self-test`, then `/ntm:schedules --setup`.
7. The success message comes from a passing self-test.
8. The Settings document holds no schedules; the scheduled tasks are the source
   of truth.
9. The Profile lives in the Style document, read by the base's `style`
   (tentative: one extra read per message).
10. No predefined job skill; jobs are composed from base skills, the weekly one
    suggested.
11. The user plugin holds two skills: `backend` (everything about the user's
    list, including where every document lives) and `notify` (their channel,
    plus the Pushover keys when they use Pushover).
12. `settings` and `ready-check` stay base skills. `ntm:settings` asks
    `ntm-user:backend` for the Settings document, then shows it or points to
    where a change goes (it loads the whole backend skill; accepted).
    `ntm:ready-check` is the same for everyone; its one tailored step asks
    `ntm-user:backend` to ping.
13. Documents `Settings`, `Style` and `Paused dates`, the last with an
    explaining line.
14. Setup saves at the end of each area, values and assets together.
15. Each database is created by its owner skill on first write; setup creates
    Settings and Style and confirms the rest's names.
16. The user plugin's `major.minor` mirrors the base's.
17. Integration branch `release-0.4`, with main's required checks.
18. Every PR has one human concern, mostly under 100 lines in 1 to 5 files.

Also decided: no migration from 0.3; no design for a duplicate Linear
connection; parents and sub-tasks are the backend's task hierarchy and stay;
conventions' mission prose is already gone from main.
