# ntm 0.4 build plan

A working plan for the owner and the worker agents: how the work runs, what's
done, what's next and what's deferred. The 0.4 shape and the patterns every
rewritten file follows are in `.claude/DECISIONS.md`, and setup's flow is in
`.claude/plans/0.4-setup-flow.md`; this file doesn't repeat them.

## How the work runs

The owner's reviews of #116, #117 and #120 set this. Where those three PRs
landed is the target for all work, not only the rewrite: the PR loop below, and
lean, intentional writing.

### The PR loop

1. One skill, agent or database template per PR, against `release-0.4`. A small
   fix that fits a PR already in hand goes into that PR.
2. The rewrite is drafted beside the current file, as `SKILL-new.md`. An agent's
   draft goes in `drafts/`, as `drafts/<name>-new.md`, because every file in
   `agents/` loads as an agent.
3. The owner reviews the draft. Each round of his comments is a new commit.
4. When he approves, the draft's text replaces the current file and the draft
   file goes.
5. A second agent does a comprehension pass: could a person follow this? It is
   never a hunt for edge cases. Fable runs only when the owner says so.
6. Squash-merge, with a written message.

### Pace

Stay at most one or two PRs ahead of the owner's review. His reviews reshape the
design, and drafts built further ahead get reworked or closed.

### The bar

For every PR: one concern a person would name as a change; intentional,
targeted, human-knowable and maintainable; mostly under about 100 changed lines,
in 1 to 5 files. A PR that adds, drops or renames a skill or agent updates
`tests/expected/` itself and says so. Versions are set at merge.

### Lean, intentional writing

An agent's default is too many words, and dense text goes unread. Write
intentionally: every line earns its place. The writing patterns in
`.claude/DECISIONS.md` hold for plans and notes too.

## Next: the rewrite wave

The database templates first, then one skill at a time, in the order a new user
meets them:

1. The templates for Settings, Style, Paused dates, Message history and Price
   watch stores, one PR each. Setup creates every database from them, so they
   land before its rewrite; they may still change then.
2. `setup`: the wizard walks its ten steps over its reference files, and creates
   every database from its template. Its persona, features and model steps are
   still to write.
3. `self-test`: the first thing a new user runs after setup. It also has to pass
   with no user plugin installed.
4. `today`.
5. `reminder`: gathers the day's facts and hands the messenger
   `type: reminders.<type>`. Once it covers them, the morning, afternoon and
   evening reminder skills go.
6. `plan`.
7. The rest, in the order the owner picks: `show-completed`, `fix-task-list`,
   `pause`, `settings`, `ready-check`, `style`, `help`, `price-watch`,
   `sync-price-watch-to-amazon` and the shopper.

The draft PRs open now were written before these patterns. Each is reworked or
closed when its skill's turn comes; none is a reason to start early.

## Then: the build and the release

Still to build, after the skills they depend on.

### The build

`setup/references/build.md`: a guide that says, per file, what the user plugin
holds and where each piece comes from.

Some text is written from the guide with the user's values (the Built line,
plugin.json, where each document lives). The rest is copied as written from a
base reference, never retyped (the rules for their features, the Linear
operations, `.mcp.json`, their notify channel).

Last check: no angle brackets in any description. Then zip, install, and hand
off with the one prompt.

### The user plugin

What the build writes: `.claude-plugin/plugin.json`, `skills/backend/SKILL.md`,
`skills/notify/SKILL.md`, and `.mcp.json` for Linear users. Its version is
`0.4.<rebuilds>`.

### The update skill

`update`, and `update/references/0.4.md`, which tells a 0.3 user the order: turn
off or delete the 0.3 jobs, install the 0.4 base, run setup.

### The help skill

`help` reads the newest installed copy when several sit side by side.

### Docs and tests

The README describes the two plugins and the first steps, and takes in
`CONNECTORS.md`. A privacy page says what leaves a run. A test holds the build
to the expected user plugin skills.

### The owner's fresh install

In the order `0.4.md` gives. Findings become small PRs on `release-0.4`.

### Release

`release-0.4` merges into main, and the version is tagged there.

## Deferred

After 0.4.0, or when the owner raises them.

### Weekday and weekend message rules

Message rules that differ by weekday and weekend. Weekend reminders would plan
nothing and cover only tasks planned for that day.

### A closer look at the Message rules template

The owner asked to be reminded at a calm point.

### A quiet evening

The evening reminder skips the push when everything was done by the afternoon
and nothing changed since.

### Recurring reminders

At an interval (pet care, medicine), where the next date follows from when it
was last done. Likely 1.1; needs the weekend reminders.

### A price watch talk

Its default pattern makes too much busywork, and setup needs better guidelines.

### Slipping tasks

Planning keeps a mention history, a date per task per reminder, and passes each
task's count through the messenger to the style, which only maps a count to a
level.

### Recent completions for fix-task-list

`fix-task-list` reads the whole closed history every week, a cost that grows.
Proposed: only recent completions.

### A tidy task review log

`fix-task-list` asks the estimator to keep the task review log tidy.

## Unknowns: one experiment each

### A subagent after a mid-session install

Can a subagent load a just-installed plugin's skill and create a scheduled task?
Decides whether the handoff runs in a subagent.

### The bundled Linear connector

Does it ask for its own sign-in, and does a job created afterwards carry it?

### An extra field in plugin.json

Does the uploader accept an extra `generated` field? If not, the description
carries the date.

### A job reaches the user plugin

Does a job whose prompt loads `ntm:today` also load `ntm-user:backend` and reach
the messenger agent?

### The cost of reading Settings and Style

How long does one read of a Settings section, and of the Style document, take
from a job on Linear? If the Style read costs too much, the build copies the
persona into `ntm-user`.

### The size of the backend skill

How big is `ntm-user:backend` for a Linear user with both features, and with
task management only? 0.4 is for tokens; this proves it.

### A list in a Claude Doc or an artifact

Does a list built in one work from a job? Until it does, setup offers only what
passed.

### Where installed plugin files sit

Where are they, for reading an agent's file and the README?

### Where the build folder goes

`/tmp` or the working directory?
