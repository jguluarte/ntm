# ntm 0.4 build plan

Written 2026-11-08 for the owner and for the worker agents, from
`.claude/DECISIONS.md` (0.4: decided, 0.4: setup, Deferred and open) and the
2026-11-07 review; revised the same day after three critics read it (Review
notes, at the end), and again after the owner answered the plan's open decisions
(section 9, Decided). Names not settled in section 9 still wait on the owner's
yes (section 6).

Words: "the base" is the published plugin, `neurodivergent-task-manager`. "The
user plugin" is the generated one, `ntm`. "The Settings document" is the
document in the user's backend that holds their values; "the Style document"
holds their persona's Profile. "Entry skill" is a six-line skill in the user
plugin that loads one base skill by name.

## The shape in one page

- The base keeps every procedure that is the same for everyone as a static skill
  or agent: conventions, plan, today, show-completed, fix-todo-list, pause,
  review-todo-list, the three reminders, price-watch,
  sync-price-watch-to-amazon, help, the three agents. It gains `setup`,
  `update`, `jobs`, `style`, and a `self-test` that passes alone.
- The user plugin carries what varies per user: five contracts (`todo-list`,
  `ready-check`, `notify`, `style`, `self-test`), `settings`, the Linear
  connector when they're on Linear, and one entry skill per base skill their
  features use. Feature-specific base text sits in per-feature references, so no
  user's run loads text that user doesn't need. Jobs and the user only ever type
  `/ntm:...`.
- Values that change live in the Settings document, read by heading. The plugin
  is rebuilt only through setup's build step: when a baked-in choice changes
  (backend, channel, features) or the base's minor changes. A base patch reaches
  every user with no rebuild, because the procedures are in the base.
- The persona's Profile lives in the Style document, in the sections
  `style/references/persona-contract.md` requires; `ntm:style` loads the base's
  `style`, which reads it (tentative: one extra document read per message; the
  fallback is copying the persona into `ntm:style` at build).
- No predefined skill for any job. A job is composed from skills however the
  user wants; the suggested weekly one is show-completed for the span just past,
  fix-todo-list, plan --auto for the next span, then one message. Each step is a
  base skill, so fixes still reach everyone.
- Setup is one wizard skill with a reference file per step, cut from today's
  configure skills. It saves at the end of each area (the todo list, the
  persona, task management, price watch, ...), values and assets together. Its
  last step builds the plugin, installs it, and has self-test run in a new chat
  (or a Cowork subagent).
- Schedules in the Settings document are a staging area only. A passing
  self-test creates the staged jobs, deletes those lines, and sends the success
  message; from then on the scheduled tasks are the source of truth, and a
  change to a job edits its scheduled task directly.

## 1. The base plugin: every file

### Rules that apply to every base file

- Base-to-base calls use the full name: `neurodivergent-task-manager:plan`. Only
  the five contracts are called as `ntm:<name>`. After the rename a bare
  `ntm:plan` resolves into the user plugin, which has it only when that feature
  was picked, and `ntm:conventions` resolves to nothing. PR 1b does the rewrite:
  about 150 references in the kept files, from a grep (conventions 35, plan 26,
  pause 15, show-completed 11, review-todo-list 11, today 9, the price watch
  pair 18, fix-todo-list 7, reminders 10, help 2). Job prompts keep
  `Load ntm:<skill>`.
- The user plugin owns triggering. A base skill that has an entry skill gets a
  one-line description, `The <name> procedure; run as ntm:<name>`, and keeps its
  body. Full descriptions stay on `setup`, `update`, `help`, `self-test` (the
  base-only run is a publishing check) and `conventions`. Otherwise about 16
  descriptions appear twice in every session's listing, "plan my week" matches
  two skills, and a changed description goes stale in the user's copy until a
  rebuild.
- Text copied into the user plugin for tailoring (the Linear operations, the
  notify channel sections, ready-check, settings, `.mcp.json`) changes only in a
  minor release, which `update` rebuilds. A patch release changes only text the
  base loads itself.
- Feature-specific base text loads only on that feature's runs: the price watch
  steps leave `self-test` for `self-test/references/price-watch.md`; the
  $price-watch, $has-amazon-alert and $amazon-unavailable labels and the stores
  database leave `conventions` for `conventions/references/price-watch.md`, read
  by `price-watch`, `sync-price-watch-to-amazon` and the shopper. This is the
  condition entry skills were decided on: no user's run loads text that user
  doesn't need.

## 2. The user plugin

### Layout

```
ntm/
    .claude-plugin/plugin.json
    .mcp.json                     Linear users only: the connector
    skills/<name>/SKILL.md        one folder per skill below
```

No references folder, no agents, no README. The base's README is the one text;
`ntm:help` is an entry skill.

### What it contains, by choice

Always:

- `todo-list`, `ready-check`, `notify`, `style`, `self-test` (section 5).
- `settings`: shows the user their settings on request (the Settings document;
  asked about their jobs, the scheduled tasks), and points the agent to the
  right place for a change: a heading in the Settings document, a scheduled task
  (edited directly, in the shapes `neurodivergent-task-manager:jobs` gives,
  named in full since it has no entry skill), the Style document through
  `style`, or a baked-in choice through update or setup. "Turn off the evening
  reminder" lands on the scheduled task. Never rebuilds. Changes can also go
  through update or setup, or the user's agent can edit the Settings document or
  a scheduled task directly.
- Entry skills `setup`, `update`, `help`.

By backend:

- Linear: `todo-list` is the Linear guide with this team's name and id in place
  of List name and List id, the documents' location, and the Settings and Style
  documents' titles; `ready-check` pings with `get_team`. `.mcp.json` is
  `backends/linear-mcp.json` copied verbatim (decided: the user plugin bundles
  the connector). The 0.3.0 upload synced to this machine shows the shape:
  `mcpServers.Linear` is `{type: http, url: https://mcp.linear.app/mcp}`.
  plugin.json gets no server entry; a plugin's connector lives in `.mcp.json`.
- The user's own backend: `todo-list` is their description per contract heading,
  as setup wrote it with them; `ready-check` uses the tool they named for
  `ping`. No `.mcp.json`.

By feature:

- Task management: entry skills `today`, `plan`, `pause`, `show-completed`,
  `fix-todo-list`, `review-todo-list`, `morning-reminder`, `afternoon-reminder`,
  `evening-reminder`; staged Schedules lines for the jobs they picked, the
  weekly composition included.
- Price watch: entry skill `price-watch`; `sync-price-watch-to-amazon` only when
  they said yes to Amazon sync; a Shopping section; `price watch` in the Built
  line, which is what `self-test` reads.

By channel:

- `pushover`: `notify` carries the Pushover section from `notify/pushover.md`
  and reads the two keys from Notifications in the Settings document.
- `claude-push`: `notify` carries only the delivery block section.

By persona: `style` is an entry skill for the base's `style`; its Profile (or
the persona body with its `## For ntm` shim), in the persona contract's
sections, is the Style document. A plain persona is a Profile too, so the Style
document always exists after setup.

### How setup writes it: a guide, not templates

`setup/references/build.md` says, per file, what it must hold and where each
piece comes from. Three kinds of text, and the guide names which is which:

1. Written from the guide with the user's values: `todo-list` (own backend),
   plugin.json, and the Built line at the top of `todo-list`.
2. Copied verbatim from a base reference, with the user's values around it:
   `todo-list` on Linear (the operations), `.mcp.json`, `notify`'s channel
   section, `ready-check` (`ready-check.md`: the taxonomy and
   `--notify-failure`; the ping is in `ntm:todo-list`, so it needs no backend
   text), `settings` (`settings.md`). These are exact and tested; the guide says
   "as written, never retyped".
3. Entry skills: the frontmatter description from
   `setup/references/entry-skills.md`, one paragraph per base skill, the one
   home for triggering text; and this body, nothing else:

    ```
    Load `neurodivergent-task-manager:<name>` and follow it. If it
    can't be loaded, end with `<Name> FAILED: the base plugin isn't
    installed or enabled`.
    ```

Last check before zipping: no `<` or `>` in any SKILL.md description or in
plugin.json's description (the uploader rejects them). Usage lines go in the
body, never the frontmatter.

Then: zip the folder, present it (the outputs folder in chat, a path under the
working directory for Chrome), install through the accept card or Customize >
Plugins. Self-test, by host: in chat, always "open a new chat and run
`/ntm:self-test`", since chat has no subagents; in Cowork, a subagent first, and
the new chat if it can't see the new plugin. Offer to drive their browser only
when the agent has browser access. On Linear the bundled server appears with the
install and may ask for sign-in: self-test's ready-check pings through it, and
if only `authenticate` tools appear, walks the user through sign-in before
`jobs` runs.

### plugin.json

```

displayName   ntm
version       0.4.<rebuilds>                  0.4.0 on first build
description   one sentence: your ntm, your todo list on Linear,
              reminders by Pushover, in your style; no date, no
              angle brackets
generated     2026-11-08T14:30Z               (if the uploader accepts an
                                               extra field, unknown 4;
                                               else the description
                                               carries it)
```

### The Built line

`ntm:todo-list` opens with one line:
`Built: ntm 0.4.0 from neurodivergent-task-manager 0.4, 2026-11-08 14:30 UTC. Features: task management, price watch.`
Loading `ntm:todo-list` does nothing, and conventions loads it on every run
anyway; `update` reads `major.minor` and the features from it, `self-test` reads
the features. plugin.json holds the same version and time for the platform and
for `help`; build.md writes both in one step. Skills read a skill by name, never
a file by path across plugins (chat takes the locator fallback), which is why
the line lives in a skill. `ntm:self-test` stays a pure entry skill: loading it
to read a line would start a run that sends a push and writes a task.

### How jobs call into it

A job that runs one skill only loads the user plugin:

```
<title>.
Timezone: <Timezone from About you>.
[Planning: <what differs from plan's defaults>.]
[Pushover app token for this job: <token>. Hand it to every ntm:notify
call as --app-token, and to the messenger agent as app token:.]
Load `ntm:<skill>` and follow it from step 1. Its FINAL REPLY and ERROR
HANDLING are this job's.
If `ntm:<skill>` can't be loaded, end the run with this line:
`<title> FAILED: ntm:<skill> couldn't be loaded; check ntm is enabled.`
```

A composed job lists its steps in the prompt, as today's bulk planning prompt
does: the same header lines; `ntm:ready-check` first; one `Load ntm:<skill>`
step each, with its span or range and what to do on its `FAILED` line; the
messenger agent with every step's lines for one message; the final reply and
error handling `jobs` writes from `job-run.md`; the same can't-be-loaded line.
The suggested weekly job: `ntm:show-completed` for the span just past,
`ntm:fix-todo-list`, `ntm:plan --auto` for the next span, then the one message.

`ntm:<skill>` loads the base skill; the base skill runs `ntm:ready-check`, the
base procedure, the base agent, `ntm:style`, `ntm:notify`. The base's agents are
on the account like its skills, so a scheduled run has them (unknown 5 checks
this).

## 3. The Settings document

Title `Settings`, a document on the todo list like the other databases; on a
backend without documents, a task's description, as the contract says. Setup
creates it when it saves the todo list area, after the ping, through
`backends/linear.md`'s `write database` (or the own-backend description) with
the List id it just collected, never through conventions; each later area adds
its values when that area is saved. `ntm:settings` shows it; the user, or their
agent, edits it. Free text under fixed headings, read by heading; a missing
section means its defaults.

```
## About you          Timezone; Country and currency (price watch only)
## Labels             the five label lines
## Planning           Estimate pattern (blank until the first review);
                      Excluded labels from automatic scheduling
## Shopping           Amazon interface; anything about how they shop
## Notifications      Pushover user key; Pushover app token (default);
                      how they want to be notified, as written
## Schedules          staging only: one line per job not yet created,
                      <steps>: <days> <time> "<title>" [planning: ...],
                      <steps> one skill or a composition; then
                      Model: <the jobs' model>, which stays
## Deviations         anything they do differently; read last
```

Who reads each: About you, conventions (dates fallback), the shopper, and `jobs`
(cron timezone); Labels, every skill that names a $label; Planning, `plan`,
`review-todo-list`, the estimator; Shopping, the shopper, `price-watch`,
`sync-price-watch-to-amazon`; Notifications, `ntm:notify` only; Schedules,
`jobs` (from `self-test`); Deviations, conventions.

Schedules holds only what is waiting to become a job. A passing self-test
creates each staged job, then deletes its line; after that the scheduled task is
the job's one source of truth. A new feature from update stages its schedule
here the same way.

Todo list is no longer a section: Backend, List name and List id are baked into
`ntm:todo-list`, since reading the document needs them. Channel is baked into
`ntm:notify` (decided). Pushover keys follow the working default: user key and
default app token in Notifications here; a job's own app token in that job's
prompt.

### Databases and where they live

Decided: every database has one owner skill that creates it the first time it
writes, in the format that skill gives; setup creates only Settings and Style,
and confirms the names of the rest (step 8).

- `Settings`: setup; shown by `settings`.
- `Style`: setup (the Profile); revised by the base's `style` on request.
- `Paused dates`: `pause`, with a line at the top saying these are the days
  nothing gets planned automatically.
- `Message history`: `style`, with the default frontmatter
  `Keep: 60 entries or 8 weeks` when missing.
- `Task review log`: `review-todo-list`.
- `Price watch stores`: `price-watch`, in the project with $price-watch.

On Linear, all but the stores database are documents in the team; setup's step 8
says so and names them. Elsewhere, `ntm:todo-list` says where.

#### Step requirements from 0.4: setup, for the workers

Each is an acceptance check for the PR that writes that step's file.

- Step 1 (PR 11): the intro from the draft; ntm says "I", the owner is "my
  creator"; ends by confirming the timezone.
- Step 2 (PR 7): suggest a free Linear account, help create and connect it, and
  ping right then. Someone who doesn't want Linear hears it takes longer, and
  that you're happy to: read the contract and search with them until they're
  content, always offering to build the list inside Claude (an artifact or a
  Claude Doc; only what unknown 8 proved) or to find an existing tool. Saving
  the area creates the Settings document with the timezone and the list's
  values.
- Step 3 (PR 8): right after the list. Push a little when they decline: without
  a persona, ntm is no different from Apple or Google reminders. Build from
  generic parts, no show or IP named, repetition guarded. The opener: "think
  about the formula of a show you enjoy, where they can snap back at you when
  you need it, or celebrate you when you've earned it". Saving the area writes
  the Style document, in the persona contract's sections.
- Step 4 (PR 9b): a numbered list, everything or a subset: day to day task
  management, and price watch.
- Step 5 (PR 9b): task management: suggest Monday to Friday for doing things and
  Sunday for cleanup and planning the week ahead, the Sunday job as the
  suggested weekly composition; then its labels, $pending-shipment included even
  without price watch. Price watch: country and currency; the schedule, the
  owner's (daily) as the default; its labels; then Amazon sync, explaining that
  cloud agents can't reach Amazon, so this works around it; a no skips the
  Amazon labels too. Show the table (job, days, time, title). Saving each
  feature's area stages its Schedules lines with its labels and other values.
- Step 6 (PR 11): one question, "a lighter model than the one running this
  chat", worded for any AI provider, no model names. Saved as `Model:` under
  Schedules; `jobs` applies it with `update_trigger`.
- Step 7 (PR 9): for a separate app on their phone or computer, strongly suggest
  Pushover, which their phone's focus settings can treat differently; otherwise
  the AI app's own push. The keys, one test push with explicit keys, then how
  they want to be notified. A job's own Pushover app isn't asked; it stays in
  `notify/pushover.md`.
- Step 8 (PR 9c): confirm the names of the databases their features need; on
  Linear, that they live at Linear's base location and which document holds
  which. Creates none: each owner skill does on its first write.
- Step 9 (PR 10, PR 11): say what's about to happen and wait for a green light,
  leaving room for anything else they want to say. Then one narrated line per

- Step 10 (PR 13): the success message is the end of the first passing self-test
  that creates the staged jobs (section 5); a pass without scheduling tools
  leaves them staged and sends nothing. The setup chat can't load the plugin it
  just installed, and on the new-chat path never learns that self-test passed,

### update

Tiny, as decided. Its whole body: load `ntm:todo-list`; if it won't load, ask
"It doesn't look like you've run setup before, do you want to?" and on yes load
`neurodivergent-task-manager:setup`; otherwise load
`neurodivergent-task-manager:setup`, which sees the Built line and follows
`setup/references/update.md`. One rebuild path, setup's build step.

`setup/references/update.md`: read `major.minor` and the features from the Built
line; list `update/references/` (the newest file is the base's version); for
each version after theirs, read that file and offer what's new, features
included; same `major.minor`: "You're current on 0.4" and offer to change a
baked-in choice (backend, channel, features). A new feature walks its area as
step 5 does and stages its schedule in Schedules. Any change: the same green
light as step 9, then `build.md` with the existing choices carried over, then
self-test as step 9 runs it, which creates the staged job. Nothing is built,
installed or tested before the green light; self-test is never run unasked.

`update/references/0.4.md`: what 0.4 is, and that 0.3 installs start fresh
(decided: no migration), in this order: install the base; turn off or delete the
0.3 jobs; uninstall `ntm-user`; run setup, whose build uploads `ntm`, which
overwrites the 0.3 `ntm` in place rather than installing beside it (My Uploads
matches plugins by name). Done in another order, the 0.3 jobs'
`Load ntm:<skill>` lines hit entry skills with no base behind them, and the
first passing self-test creates a second set of jobs beside the 0.3 ones.

## 5. Contracts between base and user plugin

A contract is a skill the base calls by a fixed name whose text varies per user
(review Q2). Five, all in the user plugin, written out per user: `todo-list`,
`ready-check` and `notify` in full. `style` is an entry skill by decision 2, and
`self-test` one because its loop is the same for everyone. Only the names and
the lines below are fixed; the body is the user's (or, for an entry skill, the
six lines).

### `ntm:todo-list`

Loaded by conventions. Opens with the Built line. Carries List name, List id,
the documents' location, and one entry per operation of `backends/contract.md`:
`ping`, `fetch open`, `fetch closed`, `read task`, `read comments`,
`write comment`, `update comment`, `set planned date`, `clear planned date`,
`set status`, `add labels`, `remove labels`, `mark duplicate of`, `create task`,
`update task`, `read database`, `write database`. Return shapes as the contract
gives them.

### `ntm:ready-check [--notify-failure <skill>]`

Returns `Ready-check OK`, `Ready-check OK (no style)` or
`Ready-check FAILED: <failure> — <fix>`. Failures from the taxonomy in
`ready-check.md`, copied verbatim. Lives only in the user plugin (decided). On
Linear, a bundled server that shows only `authenticate` tools is
`Ready-check FAILED: Linear needs sign-in — <how>`.

### `ntm:notify`

Called as today: `--title`, `--message`, and the optional `--url`, `--priority`,
`--from`, `--app-token`, `--user-key`. Returns `Sent: <title>`, the
`NOTIFY VIA FINAL REPLY` delivery block,
`Notify TOO LONG: <cap and why>; this was <n>`, or `Notify FAILED: <why>`. Caps
stay in the channel section.

### `ntm:style [--stay-fresh] [--for <reminder>] ["<tone>"] <message>`

Returns the message, plain text, ending in a `Title:` line under `--for`.
Optional: when it won't load, callers use plain words. An entry skill for the
base's `style`, which reads the Profile from the Style document, keeps Message
history, and revises the Profile with the user on request.

The persona contract, `style/references/persona-contract.md`, fixes the Style
document's required and optional sections, settled from
`.claude/drafts/persona-breakdown.md` (its components, anti-repetition, seed
prompt; nothing from its owner-specific part). Setup's persona step writes to
it; `style` reads by it.

### `ntm:self-test`

A pure entry skill. Returns `Self-test OK` or
`Self-test FAILED at <step>: <why>`.

### Where the four live, and the self-test flow

- `ready-check`: user plugin only; `ready-check.md` verbatim.
- `self-test`: the loop is the base's `self-test`. With no `ntm:todo-list` it
  returns
  `Self-test OK (base only): nothing is set up; run /neurodivergent-task-manager:setup`
  (publishing needs the base to pass alone). With one: `ntm:ready-check` (on
  Linear, the bundled server's sign-in if it asks), the loop, the price watch
  steps from `references/price-watch.md` only when the Built line names price
  watch, then `jobs`. No scheduling tools here (a subagent, or a host without
  them): the line
  `jobs: scheduled tasks aren't available here; run /ntm:self-test where they are`,
  and self-test still passes, with the staged lines left in place. Staged lines
  in Schedules: `jobs` creates each job, then deletes those lines; on a run that
  created jobs, the success message follows, naming them (setup's set, or one
  feature's from update), in the persona through `ntm:style`, sent through
  `ntm:notify` and said in the reply. Nothing staged: no job is touched and no
  message is sent.
- `notify`: user plugin; mechanics from `notify/<channel>.md`.
- `style`: base skill for the procedure; `ntm:style` the entry; the Style
  document for the Profile, in the persona contract's sections.

### `jobs` (base, static)

The shapes from `configure-schedule`: the single-skill prompt and the composed
prompt above, the cron expression with `CRON_TZ`, `notifications: {push: true}`,
the model set with `update_trigger` from `Model:`, the jitter rule as "never on
:00 or :30" (the formula and the Pacific note go). Run by `self-test`: for each
staged Schedules line, create the job, then delete the line from the Settings
document. It reads nothing else on the account and reports no differences: once
created, a job is the user's scheduled task. A change to a job (its time, its
steps, off, on, delete) edits the scheduled task directly, in these shapes;
`ntm:settings` points the agent here, by full name, for one. "Run the morning
reminder now" is `ntm:morning-reminder` by hand, as today.

## Review notes

Three critics (decision fidelity, platform, simplicity) read the first draft.
Every "must" is in: the Linear bundle stands as decided and goes in `.mcp.json`;
decision 1 was framed as the reversal it is, with both options and the
per-feature text moved out of shared base files; the build and features line
left `ntm:self-test`; chat takes the new-chat path and unknown 1 runs in Cowork;
the success message moved into the first passing self-test; the owner's install
order is written down; base-to-base calls use the full name; the user plugin
owns triggering.

"Should" items taken: update tiny and setup the one rebuild path; the
database-format rule, since decided; the green light, narration and browser
offer; saving in setup before the build (decided as per area); step 6 in setup,
provider-neutral; step requirements quoted as acceptance checks; pure `git mv`;
the caller-held-values clause; unknown 8; the locator glob and unknown 9; the
angle-bracket check; Job run as a reference; ready-check and settings as
verbatim copies; the PR sequence split and the per-PR expected commits.

Declined, or taken only in part:

- "Infer features from the skill folders present, plugin.json the one home": a
  skill can't see another skill's existence without loading it, and loading an
  entry skill runs it; chat can't read plugin.json by path reliably. The Built
  line in `ntm:todo-list` is what skills read; plugin.json keeps version and
  `generated` for the platform. Two writes in one build step, not two homes to
  keep in sync by hand.
- "Add a jobs entry skill": not added. A change to a job edits its scheduled
  task directly, with `ntm:settings` pointing the agent there; run-now is the
  reminder's own entry skill.
- "Create missing jobs only after showing the list and getting a yes": the first
  pass creates without a second yes. Step 5 showed and settled the table, step
  9's green light covers the build, and the decision says a passing self-test
  creates the staged jobs.
- "Linear server entry in plugin.json" (one critic) against `.mcp.json`
  (another): `.mcp.json`, since the synced 0.3.0 upload shows that's where the
  platform put it.
- "Remove 'offers update' from setup" and "setup's opening does the version
  compare" are the same fix, taken as: `update` is the tiny probe-and-question
  skill, and setup's opening follows `references/update.md` when `ntm:todo-list`
  loads.
